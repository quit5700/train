# BUG-032：道岔设置方向没有外观反馈，手动列车不按设置转向

## 问题类型
核心逻辑问题 / 轻微视觉问题

## 1. 问题现象
道岔选择左转、直行或右转后，方块仍显示完全相同的十字外观；没有绑定线路的手动列车也只服从原版铁轨当时的形状，无法保证按道岔设置通过。

## 2. 根本原因
方向只保存于 `RailwayDevice`（铁路设备）数据，设置界面和红石脉冲没有把选择同步到道岔的 `RailShape`（铁轨形状）方块状态。原模型也忽略全部 `shape`（形状）变体。线路控制器只在自动线路临近道岔时设置形状，手动列车没有对应步骤。

## 3. 修改文件

## 4. 具体修复方式
建立唯一的道岔方向映射服务，把列车进入方向和左转/直行/右转选择转换为真实 `RailShape`。2026-07-30 进一步增加独立持久的 `switch_choice` 方块状态，高亮只读取该状态，不再被原版相邻铁轨更新重置。设置窗口和红石脉冲只更新选择；没有绑定线路的手动列车在距离道岔两格内锁定道岔并生成实际轨道形状，确认两端均有铁轨，否则停车。全列离开后解除占用。自动线路仍优先使用线路节点保存的方向。

## 5. 如何验证
- `SwitchRailRoutingTest` 验证向东和向北进入时三种选择的六个形状映射。
- 2026-07-30 完整 `gradlew clean build` 成功；62 项测试通过，0 失败，0 错误。
- 9 个本次新增或修改的模型/方块状态 JSON 均成功解析。
- 仍需玩家进世界确认高亮位置和手动矿车物理转向。

## 6. 下次避免
道岔业务方向、方块高亮和实际矿车轨道形状必须来自同一个映射函数，禁止分别维护三套方向判断。

## 7. 2026-08-01 重新验收与 0.2.4 修订

### 问题现象
道岔仍用白色海晶灯纹理覆盖整条路径，只有固定北侧入口的三种高亮；没有保存车辆段所在入口方向。更严重的是，`shapeFor` 把列车行驶方向当作入口方向：例如向东行驶的列车实际从西侧进入，但旧代码生成的左转形状连接东侧而不是西侧，导致显示方向与真实拐弯相反。

### 根本原因
方块状态只有 `switch_choice`，缺少实际入口与放置回退方向。模型把三种选择硬编码为北侧入口。左/直/右映射没有先取行驶方向的反方向作为真实入口，因而弯轨不包含列车来向。

### 修改文件
- `block/DeviceRailBlock.java`
- `route/SwitchRailRouting.java`
- `route/SwitchEntryDirectionRules.java`
- `route/SwitchEntryDirectionService.java`
- `FabricTrainMod.java`
- `blockstates/switch_rail.json`
- 六个 `switch_highlight_*.json` 与 `switch_rail.json`
- `SwitchRailRoutingTest.java`
- `SwitchEntryDirectionRulesTest.java`
- `SwitchModelResourcesTest.java`
- `gradle.properties`、`README.md`

### 具体修复方式
- 增加永久方块状态 `entry_direction` 与 `placement_entry`：入口和当前出口同时高亮；无车辆段时使用玩家放置朝向的反方向作为入口。
- 每秒只扫描已加载道岔，从四个相连铁轨分支沿实际轨道最多检查 64 格；发现车辆段上方铁轨时选择最近车辆段所在分支，后来连接或移除车辆段也会自动更新或恢复放置回退方向。
- 左转、直行、右转统一先由入口和行驶方向计算出口，再由同一函数生成真实 `RailShape`（铁轨形状）。设置方向时同时更新业务选择与实际铁轨形状；手动列车临近时继续读取同一映射。
- 四个方向标记使用青色钻石基色，只给入口和选定出口叠加钻石块亮色；删除海晶灯白色整条路线。
- 未修改车辆连接、编组、客户端同步或整列运动逻辑。

### 验证与边界
回归测试覆盖东西南北四种行驶方向的左/直/右真实铁轨形状、最近车辆段选择、无车辆段回退、等距时优先放置方向，以及六个高亮模型不得包含白色海晶灯。自动扫描只读取已加载区块，避免强制加载铁路沿线；最终外观与游戏内转弯仍需玩家验收。

### 已尝试失败与下次避免
固定假设北侧为入口、用海晶灯画整条白色路径、直接把行驶方向作为弯轨入口均标记为已尝试失败，后续禁止重新采用。

## 8. 2026-08-02 道岔前永久停车补充修复

手动列车接近道岔时会先取得占用锁，再检查所选出口两端是否真的连接铁轨。旧代码在检查失败后直接停车，却没有释放刚取得的锁，导致修正方向后本列车及后续列车仍可能永久停在交叉口前一格。现已在无效出口返回前成对释放锁，并加入 BUG-044 的游戏回归步骤。以后任何 `tryAcquire（尝试占用）`成功后的失败分支都必须显式释放。

## 9. 2026-08-02 0.2.12 再次修订

### 问题现象

0.2.11 只修复手动列车“出口检查失败”这一条返回路径。自动列车通过线路中最后一个道岔后，如果后方没有下一道岔，原有代码没有新的事件释放当前锁，所以两个相邻道岔中常表现为第一个正常、最后一个永久占用。

### 根本原因与修复

旧逻辑把释放时机错误绑定到“接近下一道岔”，而不是当前编组是否已经完全离开。0.2.12 为每列车、每道岔建立独立通过状态：取得锁后先等待任一车辆实际进入道岔范围，随后持续检查整列；最后一节车厢离开安全范围立即释放。断轨、脱轨、运行游标无法建立、线路删除、回收和实体消失都走统一清理入口。长编组可同时安全持有多个尚未完全驶离的道岔锁。

### 已尝试失败

0.2.11 的“只在无效出口的单个 `return false`前释放”和更早的“遇到下一道岔才释放”均标记为已尝试失败，禁止恢复。
