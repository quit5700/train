# BUG-048：卸货目的地丢失、空容器拒收与自动列车第二道岔停车

## 1. 问题类型

核心逻辑、数据保存、容器转移、车辆段发车和线路自动运行问题。

## 2. 问题现象

货车在指定站点完全卸空后，已选择的卸货站会变回空。站点相邻箱子即使存在大量空槽，只要没有预先放入同类物品，货物也不会转入。车辆段点击“立即发车”后，列车有时被诊断成手动列车，并在第二个道岔附近停止。

## 3. 根本原因

两个周期卸货入口在检测到货车库存为空后主动把 `destinationStationId（目的车站编号）`重置为 0，把“本次货物已经卸完”错误地等同于“玩家取消了长期目的地设置”。旧手动转移逻辑又先检查目的容器是否已经存在相同物品，因此从未进入空槽插入阶段。

车辆段发车存在旧兼容入口仍传入 `MANUAL（手动）`控制模式的风险。更关键的是，完整线路验证虽然已经生成 `Runtime Path Cache（运行时路径缓存）`，实际运动却仍由 `RailMotionCursor（铁轨运行游标）`逐格读取原版 `RailShape（铁轨形状）`。道岔状态或相邻方块更新后，现场形状可能与刚验证的线路分支不同，列车因而在第二个道岔报告路径中断。

## 5. 具体修复方式

删除所有“库存卸空就清除货车目的地”的写入。目的地只允许由玩家保存设置或火车头保存后按既定批量规则改变。火车头界面继续把选择保存在客户端临时状态，只有点击“保存”才发送更新。

容器插入统一分为“合并已有同类堆叠”和“写入可接收的空槽”两步；空槽不再依赖容器中已有同类物品。`CargoSlotRules（货物槽位规则）`把容量、空槽、同类物品和容器准入判断提取为可直接回归测试的纯逻辑。

“立即发车”及旧兼容发车入口统一使用 `ROUTE_AUTOMATIC（线路自动）`模式。发车前把车辆段到首节点的接入路径与完整线路缓存合并，注册到整列逻辑控制器；自动列车随后沿该已验证三维路径运动，并逐格确认铁轨仍存在。循环线路只回到线路自身的循环起点，不会重新绕回发车车辆段接入段。手动列车保持原来的现场铁轨形状和道岔选择逻辑。

## 6. 如何验证已经修好

- 先运行货运、客户端保存、车辆段、线路和列车相关的 66 项 JUnit（Java 单元测试），结果全部通过，失败 0、错误 0；随后完整干净构建中的 157 项测试全部通过，失败 0、错误 0、跳过 0。
- 回归测试明确检查目的地不会在卸空后被清零、空槽可以接收物品、窗口只在保存时发送更新、“立即发车”为自动模式，以及自动运动调用缓存路径入口。
- JAR（Java 归档）内 78 个 JSON（JavaScript 对象表示法）全部解析成功；八种语言各 226 个翻译键且占位符一致；0.2.16 已安装到 26.2 游戏目录并确认唯一活动版本和哈希一致。
- 仍需用玩家实际存档验证真实箱子卸货和自动列车连续经过多道岔；按本项目回归清单操作。

## 7. 下次遇到类似问题应避免什么

业务配置不能根据一次运行结果隐式重置；“库存为空”和“目的地为空”是完全不同的状态。线路验证产出的路径必须成为线路自动列车的唯一运动依据，不能验证时走一套图、运行时再按易变方块状态走另一套图。手动列车与线路自动列车的控制模式应在动作入口显式正向映射，避免用难读的反向三元表达式。

## 已尝试失败

- 在轻量单元测试中直接初始化 Minecraft（我的世界）的 `Items（物品注册表）`和 `ItemStack（物品堆叠）`：缺少完整游戏组件注册绑定，测试环境会先因注册表组件报错。已改用纯 `CargoSlotRules（货物槽位规则）`测试缝，不再重复该方案。
- 使用临时 Java（爪哇）NBT（命名二进制标签）读取器并混合不同来源的 Log4j（日记记录库）JAR：依赖版本冲突，无法作为可靠诊断手段。实际存档只读诊断改用受控解析方式；临时源码已经删除。
- PowerShell（微软命令行）的 `ConvertFrom-Json（JSON 转换）`无法处理方块状态文件中的空字符串属性名，因此不能用它验证全部资源 JSON；改用标准 JSON 解析器逐项验证。通过管道向 Python（蟒蛇语言）传递含中文的硬编码绝对路径又会受控制台代码页影响，最终改为从已经正确设置的 UTF-8 中文工作目录使用相对路径，验证成功；后续不得在管道源码里重复硬编码中文绝对路径。
