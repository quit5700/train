# BUG-091：1.20.1／1.20.4生产客户端快捷设置混入缺少映射表引用

当前项目根目录：本Git仓库。分类：客户端环境／方法映射／运行包配置。用户提供快捷建筑对话的启动错误通知后，纳入当前十版test8交付阻断检查。其他项目的BUG文档未导入；本记录以本仓库运行包检查和本项目生成的独立生产客户端为准。

## 现象与根因

旧test7的fabric_train_simulator.client.mixins.json列出MinecraftUseItemMixin，但没有refmap字段。Loom 1.6已生成并打包client-fabric-train-simulator-refmap.json，内容正确把startUseItem映射到Lnet/minecraft/class_310;method_1583()V；配置未引用，因此生产中间命名环境仍试图查找startUseItem并崩溃。独立开发服务器不加载客户端混入；开发命名空间检查同样不能替代此生产环境验证。

## 最小修改

仅两个旧版test8的src/main/resources/fabric_train_simulator.client.mixins.json加入明确refmap引用。新增LegacyMixinRefmapTest，防止配置再次漏掉引用。交付脚本检查最终JAR内引用和实际映射条目。其余1.21各版Loom会直接重映射注入注解，最终类不保留startUseItem；26.x原生命名无需该映射。不能无差别向所有十版引用一个不存在的旧版文件，也不把required改成false或降低defaultRequire来绕过功能。

## 验证方式

tools/production_client_startup8.py从核实的实际实例配置读取原版游戏、Fabric Loader及依赖，在本项目outputs建立隔离游戏目录，只复制本项目运行包、实际Fabric API和快捷建筑及其必要依赖；不开用户存档，不替换用户游戏目录来做红灯实验。使用真实生产KnotClient和中间命名空间，以测试7复现，再用测试8验证，不用开发环境成功冒充修好。

只有启动日志明确同时加载目标版本火车和快捷建筑、OpenAL初始化、游戏纹理图集创建并持续正常运行，才记为启动通过。没有真实目标模组的启动不得算通过。进程只结束该工具新建的临时客户端，不结束用户游戏。

## 诊断失败记录

首个脚本未先复用BUG-086的Java17参数文件编码办法，UTF-8参数文件被旧启动器按系统代码页读取，中文游戏目录乱码，启动了无模组客户端。核对加载清单发现只有Fabric Loader及原版，立即判为无效证据，结果保留为evidence/BUG-091/诊断未加载目标模组-无效.json，不能作为任何成功证明。最终默认用与缺陷通知一致的Java21；所有Windows启动参数文件按GetACP系统代码页写入，其他源码、配置、日志继续UTF-8。新增强制“目标模组确已加载”门槛，不再只凭图集加载判断。

## 最终结果

以evidence/BUG-091中的每版测试7红灯、测试8绿灯及本次最终交付报告为准。两版修改后重新构建、完整回归、原52项和7项离线回收均需匹配最终源码指纹。其余八版逻辑不改变，保留各自通过结果。未完成这些证据之前不宣布启动问题已修复。

生产启动器实测补充：Windows Java21也按启动器原生代码页读取参数文件，JEP400的虚拟机UTF-8默认不能改变启动器的解析。最终Windows参数文件统一使用GetACP，JVM内源码/配置/日志UTF-8不变；不再把“只有17需要此处理”当成跨版本保证。

错误编码创建的三个临时游戏目录已核对唯一测试目录名并移回本项目outputs/启动编码失败临时目录归档，未删除用户目录或存档。

最终结果：本项目内两版测试7均复现目标模组已加载后的class_310混入失败；测试8两版在Java17、Java21下与快捷建筑1.1.9-test18/Fabric Loader0.19.3共同启动，通过四次生产资源启动检查。运行包与源码摘要相符，完整检查及原线路/离线回收专项也已重跑。真实客户端未打开用户存档，界面实际操作仍由用户确认。
