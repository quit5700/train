# BUG-124 · 后台扣库存后被迟到的区块卸载回调覆盖（十版已验证）

当前项目根目录：本 Git 仓库 Fabric模拟火车模组。分类：数据保存／库存所有权／区块生命周期。

现象：26.1.2 的真实原生可见性补充回归在保存重进后核算出三套编组，而输入只有两套。原始案例为 H:/CodexWork/q5-arrival42/TrackingLifecycleProbe实测/mc26.1.2-0.2.42-test42-try3。NBT（命名二进制标签）检查确认：只有两列原 UUID，出发车辆段却额外保存了完整的一套车头、客车及七节货车；货物仍为原 98 件。不是第三列新发车。

根因入口：InfrastructureService.view 在完整区块暂不可读时建立后台 Mirror（库存镜像），却仍保留 BOUND（已绑定库存）中的旧实体。后台将保存库存扣成零后，稍晚的 chunkUnload（区块卸载）仍把旧方块实例当作权威，再次保存旧库存。另有无条件移除绑定可能误清掉同位置的新实例绑定。

修改计划：在后台取得库存所有权前，从当前已绑定实例取得最后完整库存快照，然后撤销该实例的绑定；后台交易继续写同一权威库存。迟到卸载只能保存仍属于自己的实例，不得覆盖后台交易或移除新实例的绑定。保留原生加载时的库存恢复机制。不根据已经损坏的历史库存猜测并扣除玩家物品，不改玩家原存档。

验证要求：新增独立 InventoryClaimProbe（库存交接探针），使用实际车辆段方块和九件库存，受控让被动区块查询暂不可用，调用真实库存镜像交易，再调用迟到的真实生产卸载入口；旧包必须明确复现扣零后回到九件，新包须保留零、重新绑定零、保存重进仍为零。它是额外的生命周期回归，不能替代十版真实双列运行、自然卸载、重进、卸货及回收。原 TrackingLifecycleProbe 的数量断言保留并重新验证。

涉及文件：十版 offline/InfrastructureService.java；独立诊断工具在 H:/CodexWork/q5-arrival42。最终逐文件校验清单和测试结果在完成后补充，当前不声明已修复。

已尝试失败的诊断方式：InventoryClaimProbe 首次编译缺少 LoadedRailWorld 导入，随后凭记忆尝试 train 包也失败；已实际搜索源文件，真实所属包为 data。只修诊断工具导入，不改生产代码来绕过错误；以后先查实际文件位置，不再猜包名。

防重复：不能以一套编组在保存数据中出现两次解释成“新发了一列”；必须把保存库存、真实方块、镜像、回收单分别核对，再建立唯一库存权威。不能放宽车头、客车或货车总数预期。
诊断夹具第一次运行未调用 Container.setChanged（容器变更提交），所以“已扣零”的前提本身不成立，不能把该轮红灯当作已复现生产交易。已按实际 dispatch 的提交顺序补齐，并对已提交前提增加强制断言；只有扣零成功且迟到卸载回到九件才算有效旧包复现。保留原失败结果，不降低数量预期。
旧包有效复现已通过：真实镜像提交后库存为零，迟到卸载回调把九件库存写回。补丁工具首次全文件搜索 remove(key) 命中 forget 和 chunkUnload 两处，断言及时阻止写代码；未把该轮旧源码构建成功当作修复。改为只限定 chunkUnload 方法，先验证十版所有替换点，再备份和写入；后续构建须先检查补丁退出码。
