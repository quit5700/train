已复现事实：

1. 26.3完整故障存档副本、完整模组环境进档时，日志明确记录将railway_data.dat.recovery.bak覆盖到当前railway_data.dat。当前文件3条线路12个设备，旧恢复备份3条线路13个设备；算法优先按条目数量评分，旧备份尽管时间更早仍胜出。游戏内线路3节点从当前9个回到旧6个。本对照实际观察到线路回滚。
2. 为隔离上述回滚，另建一次性副本排除备份文件，保留当前已保存线路。原生游戏100刻实测：实际发电机active=true，起点铁轨rawPowered=true，但InfrastructureService.powered=false、linePower=false。当前9节点线路签名与旧6节点发车计划不同，powered在比较签名处直接返回false。因此该现场的“没电”不是燃料耗尽，而是把线路计划失效混入电力判断。该诊断隔离不是最终修复。
3. OfflineTrainService对NEEDS_VALIDATION线路直接拦停；保存编辑后当前线路确实处于此状态。对旧列车的独立发车快照行为还需实测，不能仅删掉判断就宣称解决。

十版代码核对：1.20.1、1.20.4、1.21.1以test43为基线，其他七版test42；迁移文件源码SHA-256完全一致，全部存在按数量选旧备份、以当前线路签名决定电力及待校验拦停。此为共用代码缺陷范围确认，不等于十版逐个实机复现。
