# BUG-090：卸货站动态有效性、零上限回收、出站扣票与设置手势

项目根目录：本Git仓库。分类：状态同步、库存安全、计费边界与交互规则。范围：十个版本0.2.42-test8，不改动历史交付；本次均为用户明确授权的行为变更。

## 现象与原实现原因

卸货候选只按线路和站点类型筛选，没有检查实际相邻容器；打开界面后也没有刷新。界面、车辆段持久化和自动调度都把上限最小值强制为1。回收先模拟库存，任何物品放不下即整列回收失败。通行系统进站扣费并检查乘客，导致无票乘客可能连带车辆回退。方块设置快捷入口使用Ctrl，与用户最终要求的Shift不一致。

## 用户确认的最终规则

仅显示有箱子的卸货站，连接或拆除后更新，空选择保留；已失效目的站清空。上限可为0，不可负；0禁止生成和自动补车，点击原有发车按钮回收当前车辆段所属编组，按钮文字不改。货物先车辆段再相邻容器，超出容量的物品在车辆段上方按正常堆叠掉落，不再因满库拒绝全部回收。玩家先下车。随本模组列车进站不验票，步行进站仍验证有效车票；进站不收费，离站不拦截，有可用票扣一次，无票或零余额不扣。不绕过实体墙。全部十版用潜行+右键打开道岔、车站、车辆段设置，更新八语言提示。

## 修改范围

十版独立源码的StationSelectionService、货运和列车类别网络/界面、TrainInteractionEvents、TrainControllerManager、DepotNetworking、TrainDepotBlockEntity、AutomaticDispatchSchedule、DepotDispatchPrecheck、DepotDispatchService、DepotRecoveryService、新DepotRecallService；通行AccessService和Rules、入口混入与FabricTrainClient、八语言资源、对应回归场景。原模型、纹理、线路固定红三角规则、终点钳位和停站逻辑不改变。

卸货连接缓存写入RailwaySavedData，已知结果在区块卸载和重启后保留；读取不了区块不当作已拆箱。旧存档未知站点限每半秒初始化一个，避免一帧加载全部远程站点。界面仅打开期间半秒请求刷新，不覆盖未提交的列车类别和有效站点选择；过期请求仍由服务端拒绝。

回收请求按原车辆段归属而非当前线路，保存待回收UUID。离线模拟列车直接从权威货物快照回收；普通未加载实体或只加载半个编组不猜测物品、不提前删除，待完整加载后处理。零上限始终阻止新生成；回收队列不会吞掉以后新生成的编组。库存模拟与溢出实体生成失败回滚，避免多次点击复制物品。

出站以已进入核心区的记录判断，外壳的一格作为边界缓冲，触边抖动不重复收费。保存已有准入记录；重新登录站内不算出站。高速一刻穿过整个范围仍判一次出站。旁观模式不收费。

## 已尝试失败与防重复

1. 首次脚本把回收队列读取插入configure方法，出现input未定义编译错误；已定位，移到各版load/loadAdditional方法的模板读取后。不得用相同赋值文本盲定位配置方法和反序列化方法。
2. 新ProbePlayer（诊断玩家）没有真实网络连接，真实startRiding完成关系绑定后，在发送同步包时空指针。失败原日志保留于evidence/BUG-090/诊断玩家无网络连接-失败.log。仅在诊断类对“无连接且关系已完成”的结尾通知作适配，生产乘坐逻辑不捕获该错误，也不把失败当作功能通过。
3. 初版将未加载站点当成无箱子会错误清空有效站点，检查时发现后改为持久化已知连接状态，并保留未知状态，不采用大量每帧强制加载区块的方案。

## 验证

为旧规则明确变更的两条入站计费断言改为入站不扣，其余原正确预期保留；新增真实服务端乘车进站、步行阻拦、无票/零余额自由出站、有效票出站一次扣除、外壳抖动、零上限停发、箱子连接和拆除、回收箱子容量及精确溢出、车辆段归属检查。三个零上限纯逻辑测试。最终逐版完整回归、历史24项、固定方向14项、自然行车14项及运行包安装哈希以交付报告为准；未取得最终结果前不宣称修复完成。

诊断接口补充：26.3的ServerPlayer.startRiding覆盖签名与旧版不同，不能假设双参数；改为诊断工具在通用单参数调用处封装结尾无连接通知，不修改生产类。未重复使用失效的覆盖签名。

十版首次接口检查：网络注册入口沿各版已成功的playC2S/serverboundPlay适配；低版ServerPlayer用serverLevel，事件中的Player用已验证ServerLevel上下文；LocalPlayer提示低版用displayClientMessage。首轮错误日志按版本保留。后续新增共用代码必须先复用同文件已有的平台调用形式。

诊断时序补充：新增掉落物与车辆在addFreshEntity后的同一回调内尚未进入世界查询索引，立即查询不能断言数量。改为下一阶段实际刻更新后核对精确掉落数量与归属回收，未放宽数量预期。26.2/26.3的当前界面读取沿用gui.screen()，旧版保留screen字段。

掉落实体诊断场景必须保证临时区块有强制加载票据和承接地板，防止无真实玩家的专用服务器把实体所在区块标为不可查询或让掉落物落出检测高度；该设置仅用于工具临时世界，不给用户世界添加强制区块。

实际数量发现：1.21.1出现124颗钻石而非60颗，说明非单纯测试时序。根因是货车继承原版容器矿车的移除掉落逻辑：复制货物入库/掉落后未清空原货车，再discard会额外掉落原64颗。所有十版在回收成功提交后、移除实体前清空原货车；离线转换在权威快照保存成功后也清空，正常破坏车辆仍按原规则掉落。修复前数量日志逐版保留；数量预期不放宽。
新版实体空间查询在无玩家临时世界不可见，测试改用Fabric实际ENTITY_LOAD生命周期记录实体并在后续刻验证仍存在的物品堆栈，避免只用addFreshEntity返回值代替实际实体。

强制区块票据生效与实体进入ENTITY_LOAD生命周期也有异步过程，固定等12刻仍会在新版过早检查。最终测试等待“实际掉落实体已加载且目标车辆可查”的信号，最多400刻；超时仍失败，不降低精确数量断言。

保存重载又发现真实边界：原重启流程将LOADED标为LEGACY_UNCONFIRMED等待实体到达，新回收服务却按!present误当销毁并取消请求。最终只对明确DESTROYED或权威记录/清单均已不存在的情况清队；未确认记录保留，点击回收也按原始清单归属把未确认列车加入等待。不把“暂时未观察到”当“已经销毁”，不通过改测试构造为UNLOADED绕开根因。修复前重启日志保留。

最终验证：十版完整检查及每版24+14+14+7项专项共4763项通过（含BUG-091两项新增配置回归）。源码、运行包、源码包均匹配当前输入摘要。实际安装、包校验和交接路径见本次交付说明。其余八版客户端尚待用户实测，不能把服务端通过当成全部客户端已人工验收。
