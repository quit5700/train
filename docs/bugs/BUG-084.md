# BUG-084：26.3自动发车误判断轨、手动生成依赖自动线路

后续规则说明（2026-11-03）：用户明确要求线路左／直／右以可见红三角为固定基准，当前以BUG-089和test7为准。本记录的“实际驶入作为出向基准”只适用于当时版本；实际驶入仍用于轨迹几何和禁止掉头，不能据此恢复旧的方向解释规则。

项目根目录：`C:/Users/quit5700/Documents/mc虚拟线路模组/Fabric模拟火车模组`。仅使用本项目记录、代码、测试及用户授权的26.3测试存档只读轨道数据。

分类：核心寻路逻辑、控制模式隔离、错误信息同步。原版本0.2.42-test3，修复候选0.2.42-test4。范围仅26.3；其他九版代码可能有同源逻辑，但本次不改变其已交付包。

## 现象与复现

用户自动生成提示“线路存在断轨或节点之间没有完整轨道”；手动生成提示“两端都找到设备或都未找到设备”。读取测试宝箱最小轨道与设备数据，未备份、修改、启动或用精简模组打开用户存档。共提取92个相关方块以及当前六个设备、线路节点与出向，保存于`evidence/BUG-084/实际存档最小轨道快照.json`。

独立临时开发服按快照重建，复现旧版自动第一段0→1误判TRACK_BROKEN，手动返回DIRECTION_UNRESOLVED。日志与旧版读回见`evidence/BUG-084/发车复现-0.2.42-test3.json`、`发车回归-0.2.42-test3.json`。测试不加载用户世界。

## 根本原因

1. 自动寻路把节点的左右出向，按道岔固定摆放入口解释，未使用上一段实际到达的轨道。第一道岔又缺少从车辆段驶来的前一格上下文。用户线路从北驶入，道岔摆放入口却为南，导致“直行”被算成往北掉头、第二处“右转”被算向东。原线路顺序与左右设置本身不需要更改。
2. `DepotDispatchService`原先用`if (line != null)`进入完整线路校验。手动按钮也会携带界面选择的线路，因此被自动线路校验拦下，随后用通用DIRECTION_UNRESOLVED显示了不匹配的原因。
3. 自动校验已有fromIndex/toIndex，但车辆段回传只保留一个翻译键，丢失失败节点。旧客户端结果一行居中绘制，长信息溢出。

另一个正确限制：当前车辆段坐标(64,-61,52)，前向南，车厢后置间距1.25格。四节客车厢的最后一节中心在(64.5,-59.5,47.5)，需要(64,-60,47)轨道；只读检查该格为空气，尾轨只到z=48。不能为绕过错误而跳过编组连续轨道与碰撞限制。用户可以补该格轨道及下方支撑，或将编组减为三节客车厢。仅在临时测试场景补轨验证，用户存档原样保留。

## 修复文件及方式

- `WorldLineValidator.java`：第一段从车辆段接入路径取得真实前一轨道；后续段沿用上段倒数第二点。只有接入路径末点与当前源节点一致时才采用入口上下文，避免错误复用。
- `SwitchRailRouting.java`：从前一轨道与道岔的水平坐标解析驶入侧，坡道忽略Y差；缺少实际前点时才保留原固定入口后备。自动线路不改变手动道岔外观。
- `DepotDispatchService.java`：仅ROUTE_AUTOMATIC（自动模式）进行自动线路校验。手动模式使用原有设备端判向、供电、材料及编组空间检查，生成后静止、线路编号为0。
- `DepotNetworking.java`：错误载荷带翻译参数，显示实际失败节点名称；保持所有旧构造调用可用。成功信息区分手动和自动生成。多人使用时客户端和服务端均应安装同一测试版。
- `DepotSettingsScreen.java`：结果信息随内容换行与滚动，不覆盖底部按钮。
- 八语言文件：节点错误指引与生成成功提示同步翻译，保留正确占位符。
- `AutomaticIncomingDirectionTest.java`：覆盖首道岔实际北侧驶入、第二道岔右转、西侧坡道驶入与缺失前点的后备。
- `tools/probe_dispatch.py`和`tools/diagnostics/DispatchProbe.java`：真实服务端最小轨道重放、生成实体、控制模式及中文载荷编解码回归。

## 已尝试失败／明确撤回

- “要求用户手动改两个固定入口”仅是诊断变量，能使旧校验通过，却不是最终修复。当前项目原有`AutomaticSwitchRouteContractTest`明确要求窗口只保留左右直行，自动路线使用隐藏缓存且不能改手动道岔外观。撤回新增入口按钮与其临时循环代码，原测试未删除、跳过或弱化。
- 不得把所选线路清空当作手动生成的最终解决办法；必须在实际调用点隔离两种模式。
- 不得无条件放行真实断轨，或忽略四节编组的尾轨空间。
- 诊断编译不能与Gradle清理/重建产物同时进行；Windows的javac除源码`-encoding UTF-8`外，还须显式设定JVM输出UTF-8，否则编译错误可能以中文系统编码输出，导致Python读日志失败。相关诊断工具已统一加三项输出编码参数。

## 验证与风险

结果以本次版本`验证结果.json`和`evidence/BUG-084/发车回归-0.2.42-test4.json`为准。必须证明：原节点设置可直接通过；真实断轨仍失败；选择一条无节点的无效线路时仍能手动生成；四节尾轨不足仍被拦截；临时补一格后车头+四节车厢完整生成、手动静止且不绑定自动线路；自动同编组按原线路生成；中文节点名网络往返完整。

当前截图中的顶部名称改名是本轮追加并获用户明确同意的新功能，不混作旧故障根因。Jade兼容与实机结果见交付说明及`docs/验证截图/0.2.42-test4/Jade名称验证.json`。

其他九版本次未同步。所有修复的实际用户世界运行表现，仍由用户重启后验证；测试场景不等于对所有大型线路的穷尽证明。

最终结果：299项单元测试、66项服务器功能检查、6项保存重载，共371项通过；原始轨道专项14项通过，旧test3同一专项仍为红灯并保留读回结果。Jade实际客户端六项全部通过（道岔、车站、车辆段、改名刷新、默认名、模组名保留）；未安装Jade的独立服务器与界面客户端亦正常。当前两个版本的发车专项用同一快照与检查器执行。
