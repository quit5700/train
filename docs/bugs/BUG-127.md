# BUG-127 正式构建共享映射缓存文件锁

分类：Gradle（构建系统）／Loom（构建插件）共享缓存并发。

当前正式项目根目录为 H:/CodexWork/模拟火车模组/最新正式源码，Git（代码版本库）远端沿用 quit5700/train。此前同项目维护记录已同步到此处，C盘旧工程仅作为本轮验收基线，待核验后回收。

现象：0.2.42正式版首次构建1.20.1，在配置映射阶段报FileSystemException（文件系统异常），尚未开始生产代码编译。

根因：两版同时配置，Loom尝试写入共享缓存的mappings-layered+hash.2198.jar，而另一个构建仍打开该文件。原始栈明确提示“另一个程序正在使用此文件”。不是图标、游戏逻辑或中文路径解析失败。

已尝试失败：首轮两个版本并行构建；后续不再以同样并发方式重试。参考本项目BUG-086关于旧版Loom缓存的串行构建建议。

修复方式：保留首轮失败日志，待当前已启动的构建退出后，对失败版本逐一串行构建；不删除共享依赖缓存、不修改依赖或命名映射版本，不跳过原有测试。

涉及文件：正式发布管理.py（构建并发改为1）；生产Java（爪哇）源码不变。

验证：待最终串行构建、完整单元回归、正式包生产类与已验收test46逐类摘要对照、十版确认原图摘要对照完成后记录最终结果。

防止复发：此共享映射缓存下的不同旧版构建不可视为完全独立任务；正式发布脚本默认串行。不要因文件锁异常修改游戏功能或反复删除全局缓存。


## 原生诊断编译器编码

新原生图标检查工具首次调用旧JDK的javac（编译器）时，遗漏已有工具所需的JVM UTF-8选项，命令行默认代码页输出被当作UTF-8读取，产生UnicodeDecodeError，继而stderr为空引发日志拼接异常。此为工具编码问题，不是用户路径或模组源码问题。已补齐-J-Dfile.encoding／stdout.encoding／stderr.encoding=UTF-8，并显式继承已配置UTF-8的子进程环境；日志先捕获原始字节，再按明确的UTF-8或原生CP936解码，写入UTF-8文件。旧失败不计验证通过。


回收站接口自检的首次-File调用被Windows PowerShell脚本执行策略拒绝，未操作任何用户文件。后续不修改全局或用户执行策略，使用已授权交互式PowerShell命令读取本地自有脚本（显式UTF-8）并在STA会话内调用；白名单及正式发布核验仍由同一脚本执行。没有永久删除回退，也不绕过工具自动审批。
